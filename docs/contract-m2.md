# M2 contract (frozen 2026-10-15 by the main session; M1 confirmed on real hardware)

Scope: plan §5 M2 row and §3.5. Two laptops, each running the same .exe: Hub (full server) or Player (joins a hub). Become hub is included only if M1 passed clean (plan §7). Everything here extends `docs/contract-m1.md`; schemas live in `packages/shared/src/m2/`.

## 1. Household key and device pairing

- **Key**: 32 random bytes generated by the hub at setup (`settings.household_key`, stored through `secrets.encrypt`). Never leaves the hub except inside the pairing reply below. Subkeys via HKDF-SHA256 with the info strings `rj/beacon`, `rj/player-proof`, `rj/hub-proof`, `rj/wrap` (**HouseholdSubkeys**).
- **Pairing (Player first run)**: the Player wizard posts `POST /api/pair` **PairBody** `{ password, deviceName, deviceId, nonceP }` to the hub over the LAN (household source gate applies; throttled like login). The hub verifies the owner password, creates the device row, and replies **PairReply** `{ ok: true, playerId, deviceToken, householdKey (base64), hubId, hubEpoch, roomName, protocolVersion, nonceH, proof }` where `proof = HMAC(hubProofKey, "pair" | hubId | deviceId | nonceP | nonceH | hubAddress | hubPort)`. The Player verifies `proof` with the received key before storing anything (binds the key to the hub that sent it). The Player stores `deviceToken` and `householdKey` with `safeStorage`.
- **Join (every connect)**: `GET /ws?role=player&player=<deviceId>&token=<deviceToken>` then the first client message must be `auth { deviceId, nonceP, proof: HMAC(playerProofKey, "join" | deviceId | hubId | nonceP | hubAddress | hubPort) }`; the server answers `authOk { nonceH, proof: HMAC(hubProofKey, "join-ack" | hubId | deviceId | nonceP | nonceH) }` or closes with `bye { reason: 'bad-proof' }`. Only after `authOk` does the server send `state`; only after verifying `authOk` does the player follow state or publish its `/hub.json`.
- **Rotation**: on player revoke or owner password change the hub generates a new key, pushes `rekey { householdKey, keyEpoch }` to every still-authenticated player (over the device-token socket) before switching, then closes sockets. A player whose proof fails while a hub beacon is present hides Become hub and shows "Owner password changed, enter it on this laptop" (re-pair with the password).
- **Device tokens** are stored as SHA-256 hashes; replicated as hashes only.

## 2. Beacons (UDP 41234, both roles listen)

**Beacon** `{ v: 2, hubId, hubEpoch, keyEpoch, roomName, address, port, version, protocolVersion, bootId, counter, sig }` with `sig = HMAC(beaconKey, canonical JSON of the other fields)`. Receivers drop: bad sig, `address` ≠ UDP source, `(bootId, counter)` not above the last seen for that hubId. A beacon is a hint: the player opens the TCP join above before following; a hub that hears a higher `hubEpoch` runs the hub-to-hub challenge (§4) before yielding.

## 3. Rooms and groups

- `rooms` row per device: `{ deviceId, name, groupId, linkState: 'linked'|'independent', lanAddress, lastSeen }`. A **group** is one session (queue machine instance) with `{ groupId, name, leaderDeviceId }`. The hub's own TV is a room too.
- **Join popup** (player side): countdown from the remembered `linkState` (default linked); button flips it; result posted as `POST /api/rooms/me` **RoomStateBody** `{ linkState }` (device-token auth). Admin link/split: `POST /api/admin/rooms/:deviceId/link` / `/split`.
- Splitting creates a new group seeded from the room's own fallback pool and an empty queue; linking merges the room into the hub's main group and **does not** move its queue entries (they are listed to the owner for re-adding, to avoid silent duplicates).
- Per-room QR: `PlayerState.qr.lanUrl` becomes `http://<hub>:<port>/r/<groupId>`; guests on `/r/<groupId>` act on that group. `/` redirects to the main group.
- **Leader**: oldest healthy authenticated player of the group; failover after 5 s of missed heartbeats; `ended`/`error` accepted only from the leader's device token with the matching revision.
- **Delayed follower**: as in the spike (dead band 1.25 s, one seek per 2.5 s, only while PLAYING).

## 4. Replication, Become hub, demotion

- **Snapshot** (**ReplicaSnapshot**) every 10 s and on change, sent only to authenticated players: `settings` (secrets wrapped with AES-256-GCM under `wrapKey`, re-wrapped with the receiver's safeStorage at rest), `passwordVerifier`, `householdKeyEpoch`, `fallback_playlists`, `fallback_videos`, `videos` (with `refreshed_at`), `history` (last 500), `rooms`, `groups`, `players` (token hashes), `quota_log`, `search_usage`, `queue_entries`, plus **tombstones** for deleted guests/history rows since the last snapshot. Players persist it as `replica.db`.
- **Become hub** (only if in scope): shown after 20 s of lost hub and a failed re-probe of the last hub address; pressing it switches the local route set to full, loads `replica.db` as `data.db`, sets `hubEpoch = old + 1`, unwraps the API key, starts beacons. Guests' pages probe `/hub.json` (open CORS) of every known player address on WebSocket loss and `location.replace` to the new hub.
- **Hub-to-hub challenge**: on hearing a higher-epoch beacon, the lower hub opens `POST /api/hub/challenge` on the other with `{ hubId, nonce }`; the other replies `{ proof: HMAC(hubProofKey, "hub" | theirHubId | myHubId | nonce | epoch) }`; on success the lower hub switches to the redirect route set, discards and logs entries the new hub lacks, and joins as a player. Equal epochs: lower `hubId` keeps.
- **Restore** sets `hubEpoch = max(backup, current) + 1` and rotates the household key.

## 5. Backups (moved here from M1 item 13)

Backup secrets (API key, Wi-Fi password, household key) are wrapped with a key derived from the owner password (`scrypt`, separate random salt stored in the backup) so a backup restores on any machine where the password in force at backup time is known; the wizard's *Restore from backup* asks for it.

## 6. Protocol

`PROTOCOL_VERSION = 2`. A player whose version mismatches the hub installs its update immediately (desktop) and shows "Update required" until then.

## Lane clarifications (server lane, 2026-10-15)

Appended by the server lane; nothing above is changed. Implemented in `apps/server/src/household.ts`, `routes/m2.ts`, `routes/ws.ts`, `session/groups.ts`, `replica.ts`.

- **Crypto encodings.** Household key: 32 bytes, standard base64 (44 chars). Subkeys: HKDF-SHA256 over the raw key, empty salt, info = the label, 32 bytes. Proofs: base64url (no padding) of HMAC-SHA256 over the parts (numbers as decimal strings) joined with `|`; a part containing `|` is refused. Beacon `sig`: base64url HMAC-SHA256 (beacon subkey) over the canonical JSON (object keys sorted recursively, no whitespace) of the beacon without `sig`. Replay rule: a different `bootId` is accepted (restart); the same `bootId` needs a strictly higher `counter`. Wrapped secrets: base64(iv[12] ‖ GCM tag[16] ‖ ciphertext), AES-256-GCM under the wrap subkey.
- **Address binding.** `hubAddress`/`hubPort` in the pair and join proofs are the host and port the player dialled, taken by the hub from the request's `Host` header (`URL.hostname`, port default 8080). The hub's own TV window proves for `localhost` (or `127.0.0.1`) and LAN_PORT.
- **PairReply** also carries `keyEpoch` (additive; to be added to the shared schema). `deviceId` must not start with `tv-` (reserved for the hub's own TV).
- **Player socket.** `/ws?role=player&player=<deviceId>&token=<deviceToken>`; the first message must be `auth` within 10 s (else `bye { reason: 'auth-timeout' }`). An `auth` message is single-use (a repeated `(deviceId, nonceP)` is `bad-proof`). Five failed proofs from one source back off like the login (upgrade answers `429 auth-throttled`). Nothing (no `state`, heartbeat or toast) is sent before `authOk`.
- **`replicaAck { type: 'replicaAck', snapshotAt }`** (player → hub, after storing a `replica`): server-local schema `ReplicaAckMessageSchema` in `routes/ws.ts`; to be added to shared **M2ClientMessage**.
- **Rekey.** Revoke and password change rotate the key (`keyEpoch + 1`), send `rekey` to every other authenticated remote player, then `bye { reason: 'rekey' }` and close (they reconnect with the new key). The revoked device gets `bye { reason: 'revoked' }` and no key. The hub's own TV socket is left open (in-process).
- **Routes.** `POST /api/rooms/me` uses `Authorization: Bearer <deviceToken>` and the household gate. `POST /api/rooms/me`, `/api/admin/rooms/:deviceId/link|split` reply `{ room: Room, orphaned: EntryAdmin[] }` (`orphaned` is empty on split). The hub's own TV cannot be split or revoked (`409 hub-room`). `POST /api/admin/players/:id/revoke` → `{ ok: true, keyEpoch }`. `GET /api/admin/replica/status` → `{ lastSentAt, bytes, players: [{ deviceId, lastAckAt }] }` (remote players only). `POST /api/hub/challenge` is capped at 20 per source per minute (`429 challenge-throttled`).
- **Groups.** The main group's ID is `main`; split groups are `g-<uuid>`, named after the room. `?group=<groupId>` is accepted by `GET /api/session`, `GET /ws?role=guest|admin`, and the admin session, transport, queue and request routes; `POST /api/requests` takes `groupId` in the body. An unknown or merged group falls back to `main`. Admin `players` lists every group's players.
- **Leader.** Order = room creation; healthy = connected, authenticated and heard from (any message) in the last 5 s. `ended`/`error` from a non-leader are ignored.
- **Replica rows** are the raw SQLite rows (snake_case columns). `settings` = `{ data, apiKeyWrapped, apiKeyLast4, wifiPasswordWrapped, guestSecretWrapped, noticeAcceptedAt }`; the household key is never included. `quotaLog` covers the last 7 days. Tombstones: those written since the snapshot the player last acknowledged (all within 30 days before the first ack); `{ table: 'guests', id }` means "forget this guest" (drop attributions in replicated history and queue).
- **`/hub.json`** `hubAddress` is an origin (`http://<chosen address>:<lanPort>`). **Player mode** (`buildApp({ mode: 'player', hub: { address, port?, epoch, roomName } })`) opens no database and has no `app.jukebox`; it serves `/healthz`, `/hub.json` and 302s `/`, `/admin`, `/admin/*`, `/r/*` to the hub origin (path and query kept).
- `protocolVersion` reported by the hub (healthz, `/api/version`, states) is now `2`.
